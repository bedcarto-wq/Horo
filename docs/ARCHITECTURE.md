# Базовая архитектура Horo 0.1: сохранённое объяснение

> Главы об исполнении отражают синхронную базу 0.1. В 0.2.0 согласованно добавлены возобновляемые контексты; актуальная карта изменений и объяснение — TIME_RUNTIME.md. Модель сцены, хранение и история из этого документа сохранены.

## 1. Карта проекта и границы ответственности

```text
horo/__main__.py             приложение Qt и главное окно
horo/model.py                авторская модель: Project, SceneNode, Graph, Edge, Variable
horo/ports.py                единый каталог карточек и типизированных портов
horo/validation.py           целостность графа, совместимость, циклы, границы областей
horo/runtime.py              независимый от Qt интерпретатор Graph
horo/errors.py               структурированная ошибка и читаемое сообщение
horo/storage.py              локальные ресурсы, атомарный JSON
horo/history.py              история снимков документа
horo/ui/main.py              связь действий пользователя с моделью, меню, панели
horo/ui/scene.py             сцена, изображения, преобразования и камера редактора
horo/ui/graph.py             карточки, порты, линии и области циклов
horo/ui/dialogs.py           типизированные значения, параметры и переменные
horo/ui/game.py              отдельное игровое окно, клавиатура и остановка
horo/examples.py             генератор маленьких проверочных моделей
scripts/build_windows.ps1   сборка редактора на Windows
```

Сначала прочитайте `model.py`, затем `ports.py`, `validation.py` и `runtime.py`. UI удобнее разбирать после ядра: он показывает уже понятные данные, а не определяет их смысл.

**Авторская модель** — состояние, которое вы редактируете и сохраняете. **Состояние выполнения** — копия, которую меняет игра. Qt-виджеты — представление: при undo, загрузке и обычной правке они перестраиваются из модели. Нельзя восстанавливать проект по тому, что нарисовано на экране.

## 2. Модель и ID

`Project` содержит три словаря: узлы сцены, графы, переменные. Ключ каждого словаря совпадает с `id` сущности. `uid()` создаёт UUID без дефисов. ID сохраняются в JSON, undo и связях; имена можно менять и повторять.

`SceneNode` — узел дерева сцены. Он хранит имя, тип (`transform` или `sprite`), ID родителя, локальный `Transform`, относительную ссылку на картинку и ID графа поведения. `GraphNode` — **другая** сущность: карточка программы с типом, параметрами, положением и ID области цикла. Эти два вида узлов нельзя смешивать.

`Graph` содержит карточки и список `Edge`. В `Edge` записаны четыре ссылки: исходная карточка, ключ её выходного порта, целевая карточка, ключ входного порта. У связи тоже есть ID: удаление/восстановление не зависит от её индекса в списке.

`Parameter` используется для параметров и результатов функции. Имя — подпись, ID — настоящий ключ порта. Вызов получает порты `arg:<ID>`, `result:<ID>`; переименование параметра не меняет программу.

`Project.from_dict()` строит типизированные dataclass из обычных JSON-данных и вызывает `check_structure()`. Здесь проверяются версия, ID, базовые поля, безопасные ссылки, дерево сцены и начальные типы переменных. Незавершённый граф может быть сохранён: отсутствие обязательной связи проверяется отдельно перед игрой.

**Почему dataclass:** они делают поля и начальные значения видимыми, позволяют копировать и сериализовать модель без привязки к Qt. Небольшому прототипу не нужна ORM или система сервисов.

## 3. Преобразования родителя и ребёнка

Координаты: +X вправо, +Y вниз, единица соответствует одному пикселю исходного ресурса. Угол в градусах, положительный визуально по часовой стрелке. Опорная точка изображения — левый верхний угол, у transform-узла — его локальный ноль.

Локальная матрица:

```text
local = Translation(x, y) · Rotation(rotation) · Scale(sx, sy)
world(child) = world(parent) · local(child)
```

Сначала масштабируется точка, затем поворачивается, затем переносится. `Transform.matrix()` возвращает шесть коэффициентов аффинного преобразования. `multiply(a,b)` применяет `b`, затем `a`; это порядок, который легко перепутать.

Пример: родитель `(10,20)`, масштаб `(2,3)`, поворот 90°. Ребёнок локально `(5,7)`. Сначала `(10,21)`, после поворота `(-21,10)`, затем перенос: **мировая позиция `(-11,30)`**. Ребёнку не нужно дополнительно прибавлять `(10,20)` в UI — это привело бы к двойному переносу.

`Project.world_matrix()` идёт по цепочке родителей и умножает матрицы от корня. В `scene.py` та же иерархия реализована `parentItem` Qt: ребёнок получает свою локальную позицию, а преобразование родителя Qt применяет сам.

Размер экрана — `Project.width/height`, это граница видимой области, а не множитель координат объектов. Масштаб камеры — transform `QGraphicsView`; он не записывается в объект. Поэтому увеличение окна редактора и прокрутка колеса не должны двигать игру.

Для самостоятельного изменения: опорную точку менять в `ObjectItem.boundingRect()/paint()` и математике модели **согласованно**. Нельзя поменять только рисунок и оставить остальные правила прежними. Глубина дерева ограничена 128 уровнями, чтобы GUI не упал на чрезмерно глубокой пользовательской структуре.

## 4. Путь правки: UI → модель → undo

Основная функция изменения документа — `MainWindow.edit(label, callback)`:

1. Клонирует исходный `Project`.
2. Выполняет конкретное согласованное изменение.
3. Проверяет базовую структуру.
4. При ошибке возвращает исходный документ и показывает причину.
5. При успехе передаёт пару «до/после» в `History.record()` и обновляет представление.

`History` хранит до 100 пар полных снимков. Это сознательно простой выбор для маленьких проектов 0.1: удаление объекта с детьми, графа с портами и связями восстанавливается без десятков частных обратных команд. Минус — расход памяти; для больших проектов нужен переход к специализированным командам, но это не требуется сейчас.

`undo()` возвращает новый клон снимка «до»; `redo()` — «после». Новая правка очищает redo. Возврат не переиспользует изменяемый объект из истории, иначе следующая правка повредила бы саму историю.

Для сцены во время drag объект отображает текущие локальные значения. Перед началом есть один снимок; на отпускании мыши создаётся **одна** запись истории. Клик без изменений не создаёт записи и не перестраивает сцену. Для карточки графа положение фиксируется на отпускании, а не на каждом `mouseMove`.

Почему часть UI-правок отложена через `QTimer.singleShot(0, ...)`: поле/карточка может вызвать обработчик, который перестроит её же виджет. Отложенное обновление даёт текущему Qt-событию завершиться прежде, чем удалить его источник. Выбор объекта меняет выбор и свойства без уничтожения активного графического элемента.

Границы истории: импортированный файл не удаляется с диска при undo; отменяется назначение/создание объекта. Игровое состояние и компоновка панелей не входят в историю документа.

## 5. Порты, типы и связи

`ports(project, graph, node)` — единственный каталог портов для UI, проверок и исполнения. `Port` хранит ключ, подпись, тип, направление и обязательность. Ключ не меняется при переводе или переименовании подписи.

Пять типов значений: `number`, `text`, `bool`, `object`, `vector`. Красные порты имеют особый тип `exec`, который никогда не соединяется с данными. `valid_value()` явно запрещает Python `bool` как число: в Python `True` является подклассом `int`, но в Horo это отдельный тип. Числа должны быть конечными, Vector2 — ровно два таких числа. Произвольный Python-объект недопустим.

`connection_error()` проверяет существование обеих карточек/портов, направление, точное равенство типов, единственный источник входа и единственное продолжение красного выхода. Один синий выход может иметь несколько потребителей. Несколько красных входящих путей к одной команде допустимы, но один выход не разветвляется самовольно.

После временного добавления связи `connect()` запускает поиск циклов. Он рассматривает данные и выполнение отдельно. Иначе вполне нормальная синяя связь контекста могла бы неправильно влиять на проверку красного порядка.

`cycle_nodes()` использует итеративный обход, а не рекурсивный: большой граф не должен сломать проверку только из-за глубины Python-стека. Красный граф ацикличен; повторение задаётся отдельной конструкцией `repeat`.

Входы с явными default: X/Y карточки Vector2, и объект для переменной объекта в **поведении** («иначе этот»). В функции объект для такой переменной обязателен и должен быть передан явно. Вход перемещения не имеет default; пустая ссылка не становится случайно текущим объектом.

Для добавления согласованного типа карточки нужны: модель параметров, `LABELS/CATEGORIES/ports()`, валидация, `Runtime`, UI-поля и тесты. Простого добавления названия в меню недостаточно.

## 6. Выполнение «клавиша → перемещение»

```text
GameWindow.keyPressEvent
  → Runtime.key_press("Space")
  → найти старт соответствующего экземпляра графа
  → новый Frame
  → пройти красную цепочку
  → action move запрашивает object и delta
  → синяя ветвь вычисляет Vector2
  → изменить Transform объекта в копии проекта
  → перерисовать игровую сцену
```

`Runtime(project)` сначала валидирует программу, затем делает `project.clone()`. Оригинал не получает перемещения или записанные значения переменных. При новом запуске создаётся новый Runtime и все начальные состояния снова берутся из авторской модели.

`key_press()` сбрасывает общий бюджет события и находит каждый объект с подходящим поведением. У каждой цепочки собственный `Frame` с `object_id`. Если один граф назначен двум объектам, каждый получает своё событие и собственный контекст: один вызов цепочки не двигает соседний объект. Если оба слушают одну клавишу, оба независимо среагируют — это не ошибочное смешение контекста.

`GameWindow` отбрасывает системный `isAutoRepeat()` и повторный keyDown до keyUp. Сброс фокуса очищает набор нажатых клавиш. Главное окно имеет WindowShortcut, поэтому его горячие клавиши не перехватывают ввод в отдельном игровом окне.

`execute()` идёт по красным связям в цикле Python `while`. Обычная цепочка не требует рекурсии. Для каждой команды создаётся новый словарь кеша вычислений. `input()` находит синюю связь; `evaluate()` получает значение её источника. Узел Vector2 берёт подключённые X/Y либо явно видимые поля, и перемещение добавляет смещение к **локальным** x/y выбранного объекта.

**Важный смысл кеша:** внутри одного действия чистая карточка вычисляется один раз; после записи следующая команда получает новый кеш и видит новые значения. Это позволяет сценарию счётчика сначала записать `Нажатия+1`, затем проверить уже обновлённые `Нажатия > 2`.

Для самостоятельного изменения расстояния меняйте Vector2 в карточке, не `runtime.py`. `Runtime` — общие правила языка, граф — ваша программа.

## 7. Переменные и условия

Объявление `Variable` хранится в проекте, начальное значение не равно текущему игровому состоянию.

- Игровые значения: `Runtime.game` — одна запись на ID, общая всем объектам.
- Объектные: `Runtime.objects[object_id][variable_id]` — отдельные значения для каждого объекта.
- Временные запуска: `Frame.temporary` — новый набор на событие или вызов функции; run-переменная принадлежит конкретному графу через `owner`.

`store()` выбирает правильный словарь. `read` возвращает копию значения и не меняет состояние. `write` — красная команда: она запрашивает данные, проверяет тип и записывает значение. Нет «скрытой записи» при вычислении синего порта.

`if` принимает только bool и выбирает `yes` либо `no`. Вторая ветка не выполняется. Если выбранный выход не подключён, цепочка просто заканчивается. В функции 0.1 этот узел запрещён: синхронная функция поднабора не имеет ветвления.

Создание переменной из панели и из карточки вызывает один обработчик `create_variable()`. В случае карточки новая запись создаётся один раз и её ID сразу записывается в параметр карточки. Переименование меняет имя, не ID. Удаление сохраняет старые ссылки как обнаруживаемую ошибку и выводит диагностику, а не переназначает их на похожее имя.

## 8. Функции и независимость вызовов

Граф-функция имеет один `entry`, список типизированных `parameters/results`, обычные команды и `return`. Поведение вызывает её красной командой `call`. Функция в 0.1 не вызывает другую функцию; рекурсия тоже не допускается.

В `invoke()`:

1. Получить выбранный ресурс функции.
2. Запросить все входные аргументы по ID, проверить типы.
3. Создать отдельный Frame с новыми временными переменными.
4. Начать красную цепочку после `entry`.
5. На `return` собрать все результаты по ID и завершить вызов.
6. Сохранить результаты у карточки call **после** завершения.

`Frame.calls` хранит результаты в пределах этой конкретной цепочки. Другой запуск/другая функция не получает их автоматически. Если данные call запрошены до выполнения его красной команды, это ошибка, а не ноль или «прошлый результат».

Функция может вернуть ноль результатов. При нуле разрешено закончить путь без return; при наличии заявленных результатов это ошибка. Неверное количество/ID аргументов обнаруживается по обязательным портам и недействительным связям. Явная ссылка на объект — обычный параметр типа object: перемещающая функция должна получить её через entry, не угадывать объект по имени.

`Control('return', values)` — внутренний служебный сигнал интерпретатора, не пользовательское исключение. Он проходит через цикл и перехватывается только вызовом функции, поэтому return внутри тела цикла завершает всю функцию.

## 9. Цикл как область программы

`GraphNode.region` — ID владельца repeat. Корневые карточки имеют None, тело цикла — ID конкретного repeat. Это **не геометрическое выделение**: перенос карточки не меняет принадлежность к телу.

`repeat` имеет вход N, красный выход `body` и внешний выход `next`. Связь из body может вести только в свою область. Обычная красная связь остаётся в области своей исходной карточки. Это запрещает случайно повторять внешнее продолжение как часть тела.

В UI «Открыть тело» переключает область холста. Внешние данные показаны как не редактируемые карточки слева: используйте их синие выходы. У владельца цикла активен только красный выход body. Для редактирования внешних значений вернитесь назад.

`execute(repeat)` читает N один раз и проверяет целочисленность/неотрицательность. При N=0 тело не начинается. Каждая итерация вызывает исполнение тела; конец его цепочки завершает итерацию автоматически. Красной обратной связи нет.

`continue` завершает текущую итерацию, `break` завершает цикл. После цикла выполняется его внешний next. Вложенные циклы в 0.1 не поддерживаются и блокируются валидатором. Return функции пробрасывается через обработку цикла и завершает вызов.

`tick()` считает действия, вычисляемые карточки и итерации, включая пустые. Лимит 10 000 применяется к одному синхронному клавишному событию — всё событие завершается до следующего кадра UI. Он общий для функций и всех объектов, среагировавших на событие. Пустой огромный цикл не может обойти защиту.

## 10. Ошибки и консоль

`Diagnostic` хранит сообщение, ID графа/карточки/объекта и при необходимости ожидаемое/полученное значение. `GraphError` переносит её из ядра в UI.

Статическая ошибка не даёт запустить игру. Динамическая останавливает Runtime целиком; игровое окно остаётся с последним состоянием, редактор продолжает работать. Следующий F5 создаёт чистое состояние.

Консоль хранит сам Diagnostic, а не пытается извлечь ID из текста. При клике `navigate()` находит граф, область и карточку, открывает и выделяет её. Если сущность удалена после ошибки, появляется пояснение. Ошибка внутри функции ведёт в функцию, внутри цикла — в его тело.

Внутренний непредвиденный дефект GUI/исполнения не объявляется успешным результатом: выполнение останавливается, пользователь видит сообщение, traceback пишет локальный logger. Ошибки чтения/импорта обработаны отдельно и не заменяют открытый документ.

## 11. Сохранение и ресурсы

`save_project()` сначала проверяет модель, сериализует JSON без NaN, пишет временный файл в той же папке, вызывает flush/fsync и `os.replace`. Если запись/замена не удалось, существующий файл остаётся. Временный файл удаляется в finally; это проверено тестом с искусственным отказом replace.

`load_project()` не исполняет код. Он полностью читает и строит новую модель до `replace_project()`. Повреждённый JSON/неподдерживаемая версия не изменяют открытый проект, его историю и сохранённый файл.

Импорт валидирует изображение средствами Qt, затем копирует файл с именем из SHA-256 в assets. Изображения одинакового содержания не копируются многократно. Сохраняется относительный путь, а `asset_path()` проверяет выход за корень, включая разрешение символических ссылок. Undo не удаляет файлы, чтобы не повредить ресурсы, используемые другими объектами.

Тестовый ресурс XPM — текстовый формат, который Qt умеет читать непосредственно. Основное требование PNG тоже реализовано и отдельно проверяется импортом PNG. XPM позволяет сохранить собственный простой рисунок через доступные текстовые Git-инструменты без внешних файлов и зависимостей.

## 12. Как проверять и самостоятельно менять код

Сначала запускайте `pytest tests/test_core.py`, затем все тесты, затем ручной сценарий. Изменение языка требует теста как минимум на правильный путь, неверный тип/вход и reset/изоляцию. Изменение GUI требует проверки мыши и undo, не только прямого вызова Python-метода.

Безопасные места для самостоятельных настроек:

- `THEME` в `ui/main.py`: цвета/шрифты/поля интерфейса.
- `LABELS/CATEGORIES` в `ports.py`: русские подписи и категории (не ID ключи).
- `STEP_LIMIT` в `runtime.py`: предел работы; слишком большой предел ухудшит отзывчивость при ошибке.
- `History(limit=...)`: число снимков и расход памяти.
- Значения вашей программы: редактируйте граф через UI, затем изучите JSON, чтобы увидеть соответствие полей.

Не меняйте ID-порты по именам и не добавляйте eval ради «удобного» ввода. Не смешивайте authoring/runtime: иначе запуск начнёт портить сохранённую сцену и история станет непредсказуемой.

Это объяснение реализации, не фиктивный отчёт о самостоятельном написании кода школьником. Проектные решения принадлежат пользователю; исходники этой версии подготовлены с помощью AI. Пользователь должен изучить их, собрать свою демонстрацию и достоверно описать свой вклад.
