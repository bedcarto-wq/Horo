# Horo 0.2.0: время, владение работой и отмена

## Что сохранено и что было разрешено изменить

Python/PySide6, окна и панели, тема, модель сцены и локальных преобразований, типы значений, механизм вычисления данных, файловое хранение, импорт и History сохранены. Формат остаётся `format_version=1`; открытие старого проекта не переписывает файл. У старых карточек отсутствующее поле `outputs` получает пустой список.

**Явно согласованное изменение:** синхронный обход красной цепочки в существующем Runtime расширен возобновляемыми контекстами и устойчивой очередью. Ранее локальный Python-вызов `invoke()` не мог дождаться результата без блокировки; теперь незавершённый вызов представлен состоянием, а не зависшим стеком Python. Это не замена движка/UI/модели или глобальный рефакторинг.

Публичные точки `Runtime`, `Frame`, `execute`, `invoke`, `key_press`, `input`, `evaluate`, `store` сохранены. Старые программы без ожиданий всё ещё завершают готовую работу при вызове. Для ожидающей программы `execute` возвращает handle Scope; прямой `invoke` возвращает результаты, если вызов уже завершён, иначе handle. Игровое окно использует новые `start/update/key_release` и не блокирует интерфейс.

Подробное объяснение базовой модели/сцены/истории — `ARCHITECTURE.md`; его прежние синхронные главы относятся к 0.1. Актуальное выполнение описано здесь.

## 1. Запуск, вызов, ветка и итерация

`Frame` остаётся набором данных исполнения графа: объект для диагностики/контекста поведения, параметры, временные значения и завершённые результаты call. Добавлены `event` и `depth`.

`Task` — живое продолжение: текущая карточка, Frame, владелец Scope, состояние управляющего узла, флаг ожидания. Отдельными живыми задачами считаются и ожидающие управляющие команды: caller, loop controller, sequence/fork join. Это важно для честного лимита памяти.

`Scope` — группа принадлежащей работы:

- `run`: отдельное событие поведения;
- `call`: конкретный вызов с отдельным Frame;
- `branch`: выход sequence/fork;
- `iteration`: конкретная итерация, знает свой контроллер цикла.

У Scope есть parent и членство дочерних Task/Scope. Set используется **только для членства и отмены**, никогда для порядка исполнения. Исполнение упорядочено deque. Группа завершается после `sealed=True` и окончания всей дочерней работы; завершение первого листа не означает завершение всей ветки.

Пример владения:

```text
run: нажатие Space
 └─ Task: последовательность (ждёт)
    + branch: выход 1
       └─ Task: разветвитель (ждёт)
          + branch: выход 1 → wait → move
          + branch: выход 2 → move
    + branch: выход 2 создаётся только после завершения выхода 1
```

Это логическое дерево работы, не новые узлы сцены. Контроллеры остаются живыми, пока их дети не завершились; поэтому следующая итерация/выход не начинается слишком рано.

## 2. События и игровой update

`Runtime.start()` идемпотентен: создаёт «При старте» один раз на каждое прикрепление графа, после создания сцены и начальных значений. Новая игра — новый Runtime, так что старт повторится в новом сеансе.

`_dispatch()` обходится по сохранённому порядку объектов и карточек. Для каждого подходящего стартового узла создаётся новый Frame/run. Два старта одного графа или новое нажатие во время старого ожидания — разные запуски, не один общий временный словарь.

Данные события:

- все старты: этот объект, время сеанса;
- key/key_release: имя клавиши;
- frame: секунд с предыдущего update.

Данные другого стартового узла в данном запуске не подставляются. Функции получают нужные данные через явные параметры; унаследованный object_id нужен для сообщений об ошибках, он не выдаётся как скрытый аргумент функции.

`GameWindow` запускает QTimer с интервалом 16 мс и PreciseTimer. Это запрос update примерно 60 раз/с, **не гарантия** точных 60 FPS. Каждый вызов `Runtime.update()`:

1. Сбрасывает общий бюджет и увеличивает номер update.
2. Проверяет монотонное время.
3. Пробуждает наступившие ожидания.
4. Создаёт события «Каждый кадр».
5. Обслуживает готовую очередь.

Перерисовка viewport сама по себе не вызывает frame-событие. Клавиатурные события сохраняют оперативную обработку готовой работы, но **не сбрасывают бюджет**: их активные шаги относятся к текущему интервалу между update.

## 3. Ожидание

В wait есть вход N и поле default=1 секунда. Подключённый вход важнее поля. Отрицательное, нечисловое, NaN и бесконечное значение — ошибка. N=0 означает продолжение не раньше следующего update.

При достижении wait:

1. Проверить N.
2. Прочитать монотонные часы именно при входе в ожидание, не использовать устаревшее время начала кадра.
3. Сохранить следующую карточку в Task.
4. Поместить запись `(deadline, registration_order, eligible_update, task_id)` в heap.
5. Вернуть управление общей очереди.

Ни sleep, ни busy-wait, ни блокирующего ожидания функции нет. Спящая задача не вычисляет граф заново и не расходует активные шаги каждый update. Срок означает «не раньше», а не обещание исполнения в точную миллисекунду; возобновление происходит на доступном update.

Задачи просыпаются по сроку, при равном сроке — по регистрации. Проснувшиеся стоят перед вновь созданными frame-цепочками; уже готовая работа не переставляется случайно. Новый wait(0), даже если время не продвинулось, имеет `eligible_update=epoch+1` и не зацикливается в текущем update.

## 4. Устойчивая очередь и ветки

Очередь FIFO: одна команда задачи выполняется, её продолжение добавляется в конец. Чистая синяя зависимость полностью вычисляется в рамках этой команды с прежним кешем. Новые дочерние выходы регистрируются в явном порядке номеров и могут начать работу в том же update.

- `sequence`: создаёт одну branch, ждёт её целиком, затем следующую.
- `fork`: создаёт все branch в порядке выходов, не ждёт первую перед запуском второй. Сам завершается только после всех.
- Неподключённый выход: пустая завершённая branch, не ошибка.
- Обычный красный выход всё ещё имеет максимум одно соединение; произвольное разветвление проводами запрещено.

Временные переменные fork-веток **общие в одном Frame запуска/вызова**, как согласовано. Результат записи/чтения определяется устойчивым порядком команд; это не гонка Python-потоков. Другой event или call имеет другой Frame.

«Первый возврат выигрывает» означает **первую реально исполненную карточку return**, а не обязательно первый пронумерованный выход: более короткая вторая ветка может достичь return раньше первой.

## 5. Последовательно и редактируемые выходы

`GraphNode.outputs` — упорядоченный список ID, не список индексов подключений. Подпись порта 1/2/3 вычисляется по его текущей позиции. `Graph.edit_output()` добавляет ID, меняет порядок либо удаляет выбранный ID и его связи. Не меньше двух выходов.

Карточка использует существующие QGraphicsProxyWidget/поля. Кнопки ↑/↓/× и «+ Выход» отправляют изменение в существующий `MainWindow.deferred_edit()` и History. Undo возвращает сам ID и связи; перестановка не переподключает провода к другим действиям. Положение карточки не определяет порядок.

Пока sequence ждёт, у него сохранён индекс следующего выхода. Завершение branch приходит как служебное продолжение в ту же очередь, а не рекурсивный вызов следующей ветки.

## 6. Пока и вложенные циклы

Существующий `region` не заменён. Повторение использует `body` и внешний `next`; вложенный loop просто находится в области внешнего. Возвращение из редактора тела идёт к непосредственному владельцу, не всегда в корень.

Repeat по-прежнему читает N один раз. While перед каждой итерацией запрашивает bool через **новый кеш**. Первоначально false — ноль итераций. Числовой вход вместо bool не преобразуется автоматически.

Контроллер создаёт iteration Scope и ждёт всю её работу, включая fork, ожидания и функции. Конец тела завершает итерацию без обратного провода. При следующей проверке while видит актуальные записи переменных.

Данные внешней области и её предков доступны вложенному телу. Данные тела нельзя произвольно читать снаружи. Красный поток не пересекает границы тела иначе, чем через порт body.

Break/continue ищут ближайшую iteration **до границы вызова функции/запуска**. Функция не может скрыто прервать цикл вызывающего графа. Break отменяет незавершённые ветки текущей итерации и выходит из цикла; continue отменяет их и начинает следующую проверку/итерацию. Вложенный break не отменяет ожидание в соседней ветке внешней итерации. Вне тела такие карточки блокируются проверкой до запуска.

## 7. Вложенные функции и результаты

Call проверяет типы аргументов и создаёт новый Frame с `depth+1`, отдельными arguments/temporary/calls. Caller Task остаётся ждать конкретный call Scope. Остальные задачи игры работают.

После успешного завершения результаты копируются в прежний `Frame.calls[call_node_id]`, затем caller получает next. При повторном достижении той же карточки её предыдущие результаты очищаются до начала нового вызова. Данные нового call до его завершения вызывают ошибку, а не возвращают прошлый результат.

Граф зависимостей функций проверяется итеративным DFS на прямую/косвенную рекурсию. Даже ацикличный вызов ограничен глубиной 64. Исполнение вложенных calls не строит цепь рекурсивных Python-вызовов; 64 уровня проверены реальным графом.

Обычный конец функции:

- без заявленных результатов — успешное завершение;
- с результатами — ошибка, **только когда закончились все принадлежащие вызову ветки**.

Return собирает все типизированные результаты и завершает данный call Scope. Остальные его ветки, циклы, дочерние calls и ожидания отменяются. Возврат из цикла тоже завершает весь call. Другой вызов той же функции остаётся живым.

## 8. Отмена и остановка

`_terminate()` итеративно собирает потомков Scope и удаляет их Task/Scope из регистров. Их completion callbacks не запускаются. Ready-очередь и heap ожиданий очищаются от принадлежащих им записей. Затем завершается именно выбранный владелец: loop получает break/continue, caller — результат return.

Проверка `done` делает отмену идемпотентной. Нельзя дважды уменьшить число веток или повторно запустить продолжение. Уже сделанные изменения мира **не откатываются**.

`stop()` отмечает контексты отменёнными, очищает tasks/scopes/ready/sleepers. `GameWindow.closeEvent()` сначала останавливает QTimer и Runtime. Поздний Qt-callback проверяет `running` и ничего не возобновляет. При ошибке действует тот же путь очистки, редактор остаётся открыт. Новый запуск создаёт новый снимок и новое начальное состояние.

Handle, возвращённый прямым `execute()`/незавершённым `invoke()`, можно отменить `Runtime.cancel(handle)`. Это техническая точка проверки/встраивания, не новый узел языка и не система паузы.

## 9. Лимиты

- 10 000 суммарных активных шагов за update: действия, вычисленные карточки, проверки/итерации и служебные продолжения.
- 1 024 живые Task, включая спящие задачи и ожидающие контроллеры.
- 64 уровня calls, рекурсия запрещена независимо от глубины.

Пустой while(true) расходует шаги и останавливается в том же update; он не переносится молча на следующий кадр. Every-frame→long-wait сохраняет все события до достижения лимита, затем выдаёт ошибку вместо тихого пропуска.

Для unit-тестов параметры Runtime допускают меньшие лимиты и внедрённый `clock` callable. GUI использует согласованные значения по умолчанию. Поднимать их без оценки нельзя: увеличатся задержки и расход памяти.

## 10. Как проверить и самостоятельно изменить

1. Запустите `python -m pytest tests/test_time.py -q`: реальные сохранённые модели и управляемые часы, без секундных sleep.
2. Запустите весь набор для сцены, истории, хранения и Qt.
3. Пройдите ручные сценарии `TIME_GRAPH.md`, особенно остановку во время ожидания.
4. Повторите их в Windows ZIP, отдельно от source/offscreen-проверок.

Настройки: значение wait — в карточке, порядок веток — её кнопками, условие while — синим bool, число repeat — входом. Для языка изучайте `_step`, `_start_iteration`, `_call_scope`, `_complete`, `_terminate`. Для UI — `make_fields`, `edit_output`, `GraphEditor.go_back`. Не привязывайте очередь к случайным ID/позициям и не сериализуйте Task/Scope в проект.

Известные границы: нет условных стартов, паузы/масштаба времени, сохранения прогресса, потоков, физики, экспорта игры и полного отладчика. Узел вывода в консоль этим этапом не добавлялся: в задании его нет.
